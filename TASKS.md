# Kindle Highlights の Amazon 同期復旧工程

2026-11-25 作成。調査対象は `master` の `2639ea1`（プラグイン 2.3.1）。この作業票で再現結果、修正方針、検証結果を管理する。

## 目標

利用中の Amazon マーケットプレイスで、利用者が Amazon の画面で認証を完了し、Kindle Notebook のハイライトとメモを Obsidian に取り込める。既存ノートに追記した内容を保ち、同じデータを再同期しても重複しない。認証切れ、失敗、キャンセルから再試行できる。日本のアカウントを優先して確認し、実機で試せた地域・認証方法を記録する。

### 01 　 2.3.1 の再現と基準測定

1. `git status --short --branch` と `git rev-parse --short HEAD` を記録する。実機側の OS、Obsidian のアプリ版・インストーラ版・Electron 版、対象地域、使う認証方式を控える。Electron 版は、確認できる場合に起動中の Obsidian の `process.versions.electron` を参照する。
2. テスト用 Vault に 2.3.1 を入れ、保存先を専用フォルダにする。最初は `Sync on Startup` と追加メタデータ取得をオフにする。Vault を分けても同じ Obsidian プロファイルの専用セッションが再利用され得る。初回ログイン・サインアウト試験は、別のテストプロファイルなど既存セッションに影響しない環境で行う。[Electron のセッション仕様](https://www.electronjs.org/docs/latest/api/session#sessionfrompartitionpartition-options)
3. 利用者が通常ブラウザで対象地域の Notebook を開き、既知の書籍とハイライトが表示されるか確認する。同じ地域を選んだプラグインの Amazon 同期でも試し、最初に止まる段階を記録する。窓が白い、外部ブラウザが開く、パスキー・二段階認証の画面で止まる、Notebook を開けたが一覧または注釈の読み込みに失敗する、のどれかを観測する。ログイン窓の手動クローズ後に再試行できるかも確認する。
4. Node 20.x の環境で依存を入れ、基準コミットの lint・テスト・ビルド結果を記録する。ロックファイルを使わない構成なので、失敗した際は解決済み依存の版も確認する。TypeScript のパースエラーなら `npm ls @types/node typescript --all` で確認する。PR #338 の 2026-08-07 のコメントに同種の失敗報告があるため、再現した場合は原因を特定し、認証修正と独立した差分で扱う。[PR #338 の議論](https://github.com/hadynz/obsidian-kindle-plugin/pull/338)

```sh
node --version
npm --version
npm install
npm run lint
npm run test -- --runInBand
npm run build
```

完了条件は、どの入口のどの段階で止まったかと、実機・ビルドの実施可否が作業記録にあること。認証画面は利用者が操作する。記録は時刻、版、地域、既知のホスト・パス、固定のエラー分類に絞る。URL のクエリやフラグメント、Cookie、認証情報、応答 HTML、書籍名や引用本文はログ・LLM 入力・Git に残さない。

### 02 　ログインウィンドウと同期 UI の終了処理

対象は [AmazonLoginModal](src/components/amazonLoginModal/index.ts)、[SyncAmazon](src/sync/syncAmazon/index.ts)、[イベント](src/eventEmitter.ts)、[同期画面の状態](src/components/syncModal/store.ts) と必要な [起動・終了処理](src/index.ts)。

- 初期化・読み込みの失敗、タイムアウト、手動クローズ、同期キャンセル、成功を扱う。結果は一度だけ確定し、成功を確定してから窓を閉じる。各経路で所有している窓・タイマー・イベント購読を解放する。メインフレームの読み込み失敗と、正常なリダイレクトに伴う一時的な中断を区別し、上限時間で必ず復帰する。[Electron の読み込み・遷移イベント](https://www.electronjs.org/docs/latest/api/web-contents/)
- 一括同期、起動時同期、単冊再同期で失敗を各入口の終了処理に渡し、待機表示・ステータスバー・処理中フラグを解除する。単冊にも排他を適用する。プラグインの無効化時は処理を中止し、古い非同期処理が再有効化後の状態やファイルを更新しないことを確認する。
- 完了条件は、Electron とタイマーのモックで、失敗、手動クローズ、キャンセル、成功とクローズの競合、タイムアウト後の遅延イベント、直後の再試行が検証できること。テストでは起動時処理と手動処理が重複しないことも確認する。

### 03 　 Notebook 取得の期限と後始末

対象は [loadRemoteDom](src/scraper/loadRemoteDom.ts) と既存の呼び出し元。

- リスナーを登録してからロードし、失敗・タイムアウト・キャンセル・DOM 抽出例外を呼び出し元へ返す。描画待ち時間と取得全体の上限を区別し、終了時にタイマー、購読、非表示窓を片付ける。取得とログを見直し、エラー通知には操作段階と固定の理由だけを渡す。実行時には認証情報を含み得る URL や生の例外を UI・コンソールへ出さない。
- Notebook と商品メタデータの呼び出しを個別に確認する。商品情報は既存どおり取得失敗時に省略できる。リモートページの `webSecurity` は有効とし、Node 連携を無効、コンテキスト分離・サンドボックスを有効にした状態で動作確認する。地域のホスト許可は用途別に扱う。[メタデータの呼び出し元](src/sync/syncManager/index.ts#L79) · [Electron のセキュリティ指針](https://www.electronjs.org/docs/latest/tutorial/security)
- 完了条件は、モックで正常取得、失敗、無応答、抽出例外、キャンセル、重複イベント、ログからの URL 機密部分の除外を確認できること。

### 04 　セッション検証と誤同期防止

対象は [AmazonLoginModal](src/components/amazonLoginModal/index.ts)、[書籍一覧](src/scraper/scrapeBooks.ts)、[注釈取得](src/scraper/scrapeBookHighlights.ts)、[SyncAmazon](src/sync/syncAmazon/index.ts)、[地域設定](src/amazonRegion.ts)。

- 選択中の地域を処理開始時に確定する。`URL` で HTTPS、地域別の正規ホスト、Notebook のパスを確認し、認証の成否は同期時と同じセッションで Notebook の正規画面が読めることで判定する。同じ Reader ホストに着いただけの場合も検証を続ける。有効なセッションでは再ログイン窓を出さずに再利用する。
- 書籍一覧と注釈取得の両方で、利用可能な Notebook、明示的な空表示、認証要求、その他の画面を判別する。画面構造の判定根拠は 01・05 の実機観測から必要な要素だけを採り、テスト用 HTML は架空データで作る。既知の空表示が確かめられるまでは、判別できない空ページを成功扱いにしない。
- 注釈ページの途中で認証切れや取得失敗が起きたら、その書籍の部分結果は書き込まない。キャンセル時も書き込み直前に確認する。認証切れでは以後の書籍取得を止め、再ログインして再試行できる表示に戻す。失敗・中断時は同期完了イベントを出さず、`lastSyncDate` を進めない。
- 完了条件は、地域違い・紛らわしいホスト名・サインイン画面・未知の HTML・正常な空一覧・有効な書籍と注釈・2 ページ目での認証切れをテストで区別できること。`Book` / `Highlight`、ハッシュ、Markdown・Properties の形式を通じて既存データとの互換を確認する。

### 05 　実機で認証経路を選ぶ

今回の実機では Safari でパスキー認証が成立したため、まず [Safari からの取り込み案](#safari-からの取り込みと更新判定の提案) を 1 冊で試す。下表は各経路の判断に使い、地域・認証方式ごとに Kindle Notebook への到達結果を記録する。

| 01 の観測                                                                                     | 次に行うこと                                                                                                                                                                                                                                   |
| --------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 通常ブラウザでも対象 Notebook に入れない                                                      | 地域、アカウント、Amazon の画面表示を利用者が確認し、Notebook が開ける条件を確定する。                                                                                                                                                         |
| Obsidian で Notebook が表示された                                                             | 同じセッションで一覧と注釈が取れるかを確認し、最初に壊れる箇所を 03・04 で直した差分と照合する。                                                                                                                                               |
| 古いインストーラで認証の表示エラーやパスキー失敗が出る                                        | Obsidian 公式インストーラの現行環境で再測定し、アプリ版、インストーラ版、Electron 版と結果を記録する。更新前後の結果から差分の必要性を判断する。[Obsidian の更新手順](https://obsidian.md/help/updates)                                        |
| 通常ブラウザでは成功するが、Obsidian では外部ブラウザへ遷移する、または認証操作を完了できない | 認証済みのブラウザ内で注釈を取得する案を先に試す。Obsidian 内の経路を再評価する場合は、#338 を原因の参考にし、ホストの遷移保護と正式なパスキー認証を使える経路を確認する。[PR #338](https://github.com/hadynz/obsidian-kindle-plugin/pull/338) |

Obsidian 内で認証を完了できる経路があれば、利用者が正式な Amazon 画面で操作し、04 の条件で確定する。遷移を扱う実装は、確認済みの HTTPS ホストとパスに絞り、想定外の遷移や新規ウィンドウを拒否する。パスキー・二段階認証の扱いは実測を根拠とする。

Safari からの書き出しが成立しない場合や、Obsidian からの定期同期が必要になった場合は、外部ブラウザの専用プロファイルで認証と取得を行う方式を比較する。認証操作は Amazon の画面で利用者が行い、そのプロファイルの中で Notebook を開く。対応端末・認証方式、導入手順、起動・終了とサインアウトを試作で確認する。[Playwright の専用プロファイル仕様](https://playwright.dev/docs/api/class-browsertype#browser-type-launch-persistent-context)

完了条件は、採用する経路で利用者が認証し、同じセッションで対象 Notebook と既知の一冊の注釈を取得できること。成立する経路がない場合は Amazon 同期の完了を保留し、判明した制約を記録する。端末に `My Clippings.txt` がある場合は既存の取り込み機能で作業を継続できる。[既存の同期方法](README.md)

#### Safari からの取り込みと更新判定の提案

Safari の Kindle Notebook で利用者が書き出しを開始し、書籍・注釈だけをローカルの JSON として Obsidian に渡す。認証は Safari のセッションに留める。初回に全冊を取得し、以後は確かな更新指標が確認できるまで全冊の注釈を比較する。現行のテンプレートと差分処理を活かし、変更のないノートの再書き込みを避ける。

| 判定に使うデータ                             | 用途                                                                                                                                                                                                                                                                                                              |
| -------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 地域と ASIN（Amazon の商品 ID）              | 前回の取得記録と照合する。Amazon 上の書名が変わっても同じ本として扱う。既存ファイルへの書き込みは現在の `bookId` と ASIN の対応を確認してから行う。                                                                                                                                                               |
| 書籍一覧に表示される注釈件数と最終アクセス日 | 値が得られれば取得候補の優先付けに使う。行数は、画面の折り返しや Markdown の書式に左右されないよう、Notebook の注釈レコード数として数える。日本の一覧が本ごとの件数を提供するかは未確認。最終アクセス日は閲覧でも変わるという上流報告がある。[PR #343](https://github.com/hadynz/obsidian-kindle-plugin/pull/343) |
| 各本の全ページから取得した注釈の内容         | 本文、メモ、位置・ページ、色を一定の形式にそろえ、前回取得した内容と比較して更新を確定する。比較用ハッシュには注釈の件数と内容を含める。件数が同じメモ編集や、1 件の削除と 1 件の追加も区別する。                                                                                                                 |

1. **1 冊の試作。** Safari で書籍を開き、ASIN と画面の注釈を JSON に書き出す。バージョン、地域、書籍、注釈、取得が完了したかを判定できる情報を持たせる。初期検証は利用者の操作で行い、小さい範囲で JSON と実際の表示を照合する。Obsidian では `Book` / `Highlight` に変換し、同じ 1 冊を 2 回取り込んで重複がないこと、1 件追加すると 1 件だけ追記されることを確認する。[既存の書き込み処理](src/sync/syncManager/index.ts#L41)
2. **一覧と注釈の全ページを取得する。** 書籍一覧は遅延読み込みを含め、ユニークな ASIN を数えて利用者の Notebook の範囲と照合する。1 冊に複数ページある場合は全ページを取得してから比較する。取得が途中で止まった本は未完了に戻し、再試行に含める。空の注釈一覧は、正規の画面で取得完了を確認できる場合に記録する。
3. **初回の比較データを保存し、次回の追記を絞る。** 本ごとに最後に全ページを確認できた時刻と比較結果を持つ。既に取り込んだ本の Markdown・Properties を保持し、確実に追加された注釈を既存処理で追記する。メモの編集や削除を検出した場合は最初の版では結果に示す。対応関係が曖昧な変更も確認対象とする。書き込みに失敗した本は再試行に残す。既存の処理はハイライト ID を使って未収録分を探すため、比較用ハッシュは既存の ID やブロック参照と独立させる。[既存の差分判定](src/sync/diffManager/helpers.ts#L29)
4. **件数を使った絞り込みを検証する。** 同じ本を開くだけの場合、注釈の追加・削除、同日中のメモ編集、件数を変えずに 1 件を入れ替えた場合を試す。書籍一覧にすべての変更に追従する値が確認できれば、一覧から候補を選び、その本の詳細を取得する。件数を得るために本の詳細を開く必要がある場合は、開いたページからそのまま内容まで比較する。
5. **速度と反映の範囲を確認する。** 実データで一覧取得、注釈取得、ローカル比較、書き込みの時間を分けて測る。自動テストは架空の 200 冊を用意し、そのうち 10 冊だけ注釈を変えて、検出 10 冊と未変更 190 冊を照合する。更新した本が分かっている場合に備え、選んだ本だけを確認する操作も候補にする。高速モードを追加するなら、確認候補に加えて前回確認が古い本も一定数ずつ巡回する。1 回の巡回冊数は実測して設定し、未確認冊数を画面で示す。

一覧に信頼できる指標がなければ、「詳細の取得は 200 冊、変更の検出は 10 冊」という動きになる。以前の 30 秒〜2 分という概算は詳細取得を 10 冊に絞れた場合のものなので、まず全冊確認を実測する。Web Clipper や Kindle アプリからの書き出しは、数冊の退避や書き出しデータの確認に使える。Kindle Bridge を比較する場合は、同じアカウントでのパスキー、一覧で取得できた冊数、複数ページある本の注釈件数を同じ条件で確認する。[Web Clipper](https://obsidian.md/help/web-clipper) · [Kindle Highlights Importer](https://community.obsidian.md/plugins/kindle-html-importer) · [Kindle Bridge](https://community.obsidian.md/plugins/kindle-bridge)

### 06 　サインアウトと地域切替

対象は [セッション消去](src/scraper/session.ts)、[設定画面](src/settings/index.ts)、[設定ストア](src/store/settingsStore.ts)。

- Electron 経路では既存の専用パーティションを再利用し、サインアウトはそこだけを消去する。セッション API が使えない場合に一時ウィンドウを使うなら必ず閉じる。消去成功後に設定の表示を更新し、消去失敗は UI に返して再試行可能にする。外部ブラウザ経路を採用した場合は、専用プロファイルのセッションのみを扱う。
- `isLoggedIn` の保存値は表示の補助として扱う。地域を変更したら接続状態の表示を更新し、次の同期でその地域のセッションを確認する。進行中の同期が別地域のデータを取りに行かないようにする。
- 完了条件は、消去の成功・失敗、地域変更、再起動後のセッション再利用、期限切れ後の再認証が対象環境で確認できること。
